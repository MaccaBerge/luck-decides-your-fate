# v1.1 — Production Readiness (Luck Decides Your Fate)

v1 is complete and works on the local network. v1.1 makes the codebase **production-ready for Railway behind Cloudflare** and documents the deployment. It adds **no new product features** (the one exception is a small admin backup download).

- **Executor:** a single Claude Code session (no agent team needed).
- **Spec for everything else:** `docs/v1-plan.md` and `CLAUDE.md`. Do not change API contracts, URL paths, or secrecy behavior from v1 unless this plan says so.
- **Branch:** `chore/v1.1-production-ready`. Commit per requirement. Open a PR to `main` when all validation passes. **Do not merge.**

---

## 1. Production Target

```
luckdecideyourfate.com ─┐
www.luckdecideyourfate.com ─┼─ Cloudflare 301 redirect (keeps path + query) ─┐
www.luckdecidesyourfate.com ─┘                                               ▼
                                     luckdecidesyourfate.com ──HTTPS──► Cloudflare DNS ──► Railway
                                                                                     │
                                                                  one Docker container (1 replica)
                                                                  FastAPI + built React frontend
                                                                                     │
                                                                  Railway volume mounted at /data
                                                                  (/data/luckdecidesyourfate.db)
```

Hard constraints:
- **Exactly 1 replica, 1 Uvicorn worker.** Live sockets, spin locks, admin sessions and the new rate limiter all live in memory.
- The app sits behind a proxy (Railway, optionally also Cloudflare). It must trust forwarded headers for scheme and client IP.
- Every redeploy restarts the container. In-memory state is lost: sockets reconnect and the admin must log in again. This is accepted.

### R1 — Dockerfile
- Multi-stage: a Node LTS stage builds `frontend/dist`; a Python 3.12-slim stage installs `backend/requirements.txt` only (not the dev requirements).
- Copy `backend/app` and the built `frontend/dist`. Set `FRONTEND_DIST` to that location.
- Run as a **non-root user**. The `/data` directory must exist and be writable by that user.
  - **Railway exception (decided):** Railway mounts volumes owned by root, so a non-root process can't write to `/data` there. On Railway, set `RAILWAY_RUN_UID=0` (runbook §6.2), which runs the container as root on Railway only. The image itself stays non-root for local runs and other hosts. - The `CMD` must be **shell form** so `PORT` expands:
  ```dockerfile
  CMD uvicorn app.main:app --host 0.0.0.0 --port ${PORT:-8000} --workers 1 \
      --proxy-headers --forwarded-allow-ips="*"
  ```

- No `--reload`. `EXPOSE 8000` is for documentation only.

### R4 — Client IP behind proxies
Add `get_client_ip(request)` (or the WebSocket equivalent if needed), used by the rate limiter. Priority:
1. the `CF-Connecting-IP` header (set by Cloudflare when proxied)
2. the first entry of `X-Forwarded-For`
3. `request.client.host`

Document in a code comment that these headers can be spoofed when the app is reached without a proxy in front. That's acceptable for this app.

### R5 — Admin login rate limiting
- In memory: track **failed** login attempts per client IP in a sliding window of `LOGIN_RATE_LIMIT_WINDOW_SECONDS`.
- Once an IP has `LOGIN_RATE_LIMIT_ATTEMPTS` failures inside the window, **every** login attempt from that IP (including a correct password) returns:
  - **429** `{"error": {"code": "too_many_attempts", "message": "Too many login attempts. Try again later."}}`
  - a `Retry-After` header (whole seconds until the oldest failure leaves the window).
- Successful logins don't count as failures. Old entries are pruned so memory doesn't grow forever.
- Frontend (`src/admin/LoginPage.tsx`): on 429, show the message and disable the "Log in" button for the `Retry-After` seconds.
- Add `too_many_attempts` (429) to the error-code table in `docs/v1-plan.md` §8, or in a new `docs/api-changes-v1.1.md`.

### R6 — Health check
`GET /api/health`:
- Runs a trivial DB query (`SELECT 1`).
- 200 `{"status": "ok"}` on success (unchanged contract).
- 503 `{"error": {"code": "unhealthy", "message": "Database unavailable"}}` on failure.

Railway uses this path as its health check.

### R7 — robots.txt + noindex for admin
Served by the backend at `GET /robots.txt` (registered **before** the SPA fallback), `text/plain`:
```
User-agent: *
Disallow: /g/
```
**Do not list `/admin` in robots.txt.** It's a public file and would reveal that the controller exists. Instead, keep the admin area out of search engines with a header, which nobody sees by accident:
- Every response for `/admin` and `/admin/*` (the SPA-fallback HTML) and for `/api/admin/*` gets `X-Robots-Tag: noindex, nofollow`.
- Player pages and `/` do **not** get this header.

### R8 — Security & caching headers
Add a middleware that sets these on every HTTP response:
- `X-Content-Type-Options: nosniff`
- `Referrer-Policy: strict-origin-when-cross-origin`
- `X-Frame-Options: DENY`
- `Strict-Transport-Security: max-age=31536000` — **only when `COOKIE_SECURE=true`**

Caching:
- `/assets/*` (hashed filenames): `Cache-Control: public, max-age=31536000, immutable`
- `index.html` (including SPA-fallback responses): `Cache-Control: no-cache`, so new deploys reach users immediately
- `/api/*`: `Cache-Control: no-store`

No Content-Security-Policy in v1.1; it risks breaking canvas and confetti, so leave it for later.

### R9 — Graceful shutdown
On application shutdown (SIGTERM from Railway on redeploy):
1. Close all player and admin WebSockets with **code 1012** ("service restart").
2. Cancel pending spin-finish tasks cleanly; `finish_dangling_spins()` on the next startup already repairs the DB.

Frontend `openSocket` must treat 1012 like any other non-fatal close and **reconnect** with its existing backoff. Only 4401 and 4404 are final. Verify this, and fix it if needed.

### R10 — Frontend production check
- No hardcoded `localhost`, `127.0.0.1` or `:8000` anywhere in `frontend/src`. All URLs are relative, and WebSocket URLs are built from `window.location`.
- The production build works when served by FastAPI from the same origin.

### R11 — Admin database backup
- `GET /api/admin/backup` (admin cookie required; otherwise 401 envelope):
  - Create a consistent snapshot with Python's `sqlite3` backup API into a temp file.
  - Return it as `application/vnd.sqlite3` with `Content-Disposition: attachment; filename="luckdecidesyourfate-YYYYMMDD-HHMMSS.db"` (UTC).
  - Delete the temp file after sending.
- Dashboard: a "Download backup" button (`aria-label="Download backup"`) that triggers the download.
- Never reachable without auth; never linked from player pages.

## 6. Manual Deployment Steps — done by the USER, not Claude

> **Claude: do not attempt these.** You have no access to the Railway or Cloudflare dashboards and must not use their CLIs. Turn this section into `docs/deployment.md` (R13), keeping the order and the checks.

### 6.1 Before deploying
- Merge the v1.1 PR. CI must be green on `main`.
- Generate a long random admin password (e.g. 32+ characters from a password manager) and store it in the password manager.

### 6.2 Railway
1. New Project → **Deploy from GitHub repo** → select the repo. It builds from the root `Dockerfile`.
2. Service settings:
   - **Region:** an EU region (closest to Norway)
   - **Replicas: 1** (never more)
   - **Health check path:** `/api/health`
   - **Auto-deploy:** from the `main` branch
3. **Add a volume** to the service, mounted at **`/data`**.
4. **Variables:**
   - `ADMIN_PASSWORD` = (from the password manager)
   - `COOKIE_SECURE` = `true`
   - `DATABASE_PATH` = `/data/luckdecidesyourfate.db`
   - `GAME_TTL_DAYS` = `7`
   - `RAILWAY_RUN_UID` = `0` (lets the app write to the root-owned volume; see R1)
   - Do **not** set `SPIN_DURATION_*` or `PORT`. Railway provides `PORT`.
5. Deploy. Check the logs for the `config:` startup line and no errors.
6. **Volume write check:** create a rigged link in the admin, then trigger a redeploy (Railway → Deployments → Redeploy). Log in again: the link must still be there. If you see permission errors or the link is gone, the volume isn't writable or isn't mounted at `/data`. Stop and fix that before continuing.
7. Test on the Railway-provided URL (`*.up.railway.app`): wheel, admin login, a rigged link, spins.

### 6.3 Custom domain + Cloudflare DNS
1. In Railway → service → **Networking → Custom Domain**, add `luckdecidesyourfate.com`. Railway shows the DNS record to create (usually a CNAME target).
2. In Cloudflare → `luckdecidesyourfate.com` → **DNS**: create exactly the record Railway asked for. Cloudflare allows a CNAME on the root domain (CNAME flattening).
3. **Start with the record set to "DNS only" (grey cloud).** Wait until Railway shows the domain as verified with an active certificate.
4. Optional, later: switch to "Proxied" (orange cloud). If you do, set Cloudflare **SSL/TLS mode to "Full (strict)"** and test again. WebSockets work through the Cloudflare proxy. If anything breaks, switch back to DNS only.

### 6.4 Redirects (Cloudflare)
Goal: every other hostname sends a **301** to `https://luckdecidesyourfate.com` + the same path + query.

1. **`www.luckdecidesyourfate.com`:** add a DNS record `www` (proxied, orange cloud). The target can be a placeholder like `A 192.0.2.1`, because Cloudflare answers the redirect before reaching it. Then add a Redirect Rule: hostname equals `www.luckdecidesyourfate.com` → dynamic redirect to `concat("https://luckdecidesyourfate.com", http.request.uri.path)`, status 301, **preserve query string** on.
2. **`luckdecideyourfate.com` and `www.luckdecideyourfate.com`:** in that domain's Cloudflare zone, add proxied DNS records for `@` and `www` (same placeholder), plus one Redirect Rule matching both hostnames, with the same dynamic target, 301, preserve query string.
3. SSL/TLS → Edge Certificates → turn on **Always Use HTTPS** for both zones.
